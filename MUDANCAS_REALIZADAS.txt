4. ONDE O CÓDIGO LÊ O .env (COMO FUNCIONA)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  O arquivo db_inserter.py detecta automaticamente onde está o .env:

  Rodando como script .py (desenvolvimento):
    → O código sobe um nível a partir de app/ e encontra .env na raiz
    → Caminho: jd-extractor\.env

  Rodando como .exe (produção — empacotado com PyInstaller):
    → O código procura o .env na mesma pasta onde o .exe está
    → Ou seja: coloque o .env na mesma pasta do .exe gerado

  Isso é feito com essa lógica no db_inserter.py:
    if getattr(sys, 'frozen', False):
        _base_dir = os.path.dirname(sys.executable)   # pasta do .exe
    else:
        _base_dir = pasta raiz do projeto              # para .py

5. MAPEAMENTO COLUNAS EXTRAÍDAS → CAMPOS DO BANCO
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Dado da API JD (coluna do Excel)   →  Campo na tabela tb_EquipmentOptions
  ─────────────────────────────────────────────────────────────────────────────
  PIN                                →  pin            (varchar 45)
  Code                               →  code           (varchar 45)
  Description                        →  description    (varchar 255)
  Created                            →  created_at     (varchar 45)
  Created By                         →  created_by     (varchar 45)
  Deleted                            →  deleted_at     (varchar 45, nullable)
  Deleted By                         →  deleted_by     (varchar 45, nullable)
  [gerado automaticamente: NOW()]    →  created_at_db  (datetime)
  [gerado automaticamente: NOW()]    →  updated_at     (datetime)
  id_EquipmentOptions                →  AUTO INCREMENT — NÃO inserido
  CHASSI_REFERENCIA                  →  Ignorado (redundante com pin)

6. COMO O INSERT FUNCIONA — LÓGICA TÉCNICA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  INSERT INTO tb_EquipmentOptions
    (pin, code, description, created_at, created_by,
     deleted_at, deleted_by, created_at_db, updated_at)
  VALUES (%s, %s, %s, %s, %s, %s, %s, %s, %s)
  ON DUPLICATE KEY UPDATE
    description = VALUES(description),
    deleted_at  = VALUES(deleted_at),
    deleted_by  = VALUES(deleted_by),
    updated_at  = VALUES(updated_at);

  Explicação do ON DUPLICATE KEY UPDATE:
    → Se o mesmo par (pin + code) já existir no banco, em vez de duplicar,
      o registro é ATUALIZADO com os dados mais recentes.
    → Isso só funciona se existir um UNIQUE INDEX em (pin, code) — veja seção 9.
    → Sem o índice: comporta-se como INSERT normal (nenhum erro, apenas insere).

  Valores nulos:
    → Deleted e Deleted By podem vir vazios da API — o código converte para NULL.
    → Qualquer valor "nan", "NaT", "None", "" também vira NULL.

9. RECOMENDAÇÃO: CRIAR UNIQUE INDEX NO BANCO (evitar duplicatas)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Execute esse SQL UMA VEZ no MySQL Workbench no banco DEV:

    ALTER TABLE tb_EquipmentOptions
    ADD UNIQUE INDEX uq_pin_code (pin, code);

  Por que fazer isso?
  → Garante que o mesmo chassi+opção (pin+code) não seja inserido duas vezes
  → Se o sistema for rodado duas vezes com o mesmo chassi, o ON DUPLICATE KEY
    UPDATE apenas atualiza o registro existente em vez de duplicar
  → Sem esse índice o sistema funciona normalmente, mas pode gerar duplicatas
