PARTE 1 — CONFIRMAÇÃO: ISSO É UM RPA?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SIM. O JD Extractor é um RPA (Robotic Process Automation) clássico.

O que caracteriza um RPA:
  ✔ Automatiza uma tarefa que um humano faria manualmente no computador
  ✔ Interage com sistemas externos sem API própria (neste caso, simula
    um login humano via Selenium/Okta para capturar o token de autenticação)
  ✔ Processa dados estruturados em lote (lista de chassis via planilha)
  ✔ Produz um resultado consolidado (Excel + inserção no banco)

Como o RPA atual funciona (fluxo completo):

  [1] scraper.py  → Abre o Chrome via Selenium
                  → Navega para jdwarrantysystem.deere.com
                  → Aguarda o usuário fazer login manual com Okta (MFA)
                  → Intercepta o tráfego de rede com selenium-wire
                  → Captura o Bearer Token do cabeçalho "Authorization"
                  → Fecha o browser e retorna o token

  [2] processor.py → Lê a planilha .xlsx com coluna "chassi"
                   → Para cada chassi, chama a API da John Deere:
                     GET https://jdwarrantysystem.deere.com/api/products/{PIN}/options
                   → A API retorna um Excel com os equipamentos/opções do chassi
                   → Consolida tudo em um único DataFrame

  [3] db_inserter.py → Insere o DataFrame consolidado no MySQL
                     → Tabela: db_Cor_Maqnelson_RPA_Dev.tb_EquipmentOptions
                     → Usa ON DUPLICATE KEY UPDATE (sem duplicatas)

  [4] main.py → Interface gráfica (CustomTkinter) que orquestra tudo acima

Resumo: é um robô que simula um humano fazendo login, captura o token de
acesso e usa esse token para buscar dados via API em lote.

PARTE 2 — É POSSÍVEL CRIAR UM PORTAL WEB? ANÁLISE DE VIABILIDADE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

RESPOSTA DIRETA: SIM, É TOTALMENTE POSSÍVEL. Com uma ressalva importante.

O que é fácil de migrar para web:
  ✔ Upload de planilha .xlsx pelo navegador                  → 100% viável
  ✔ Chamadas à API da John Deere (GET por chassi)            → 100% viável (server-side)
  ✔ Geração do Excel de resultado e download pelo browser    → 100% viável
  ✔ Inserção no banco de dados MySQL                         → 100% viável
  ✔ Visualização de logs/progresso em tempo real na tela     → 100% viável

O que é desafiador (o ponto crítico — O LOGIN):
  ⚠ O login Okta exige interação humana real (aprovar no app do celular/2FA)
  ⚠ Isso é feito hoje em uma janela de Chrome que abre na máquina do usuário
  ⚠ Em um servidor remoto, o usuário não pode interagir com um Chrome
    rodando lá na nuvem — não tem tela!

SOLUÇÃO PARA O LOGIN — 3 OPÇÕES (detalhadas abaixo):

  OPÇÃO A — Recomendada: "Token Helper Local" (mais simples)
    O usuário roda um mini-script Python na própria máquina dele, que abre
    o Chrome, faz login normalmente e exibe o token. Ele copia e cola no portal.
    
  OPÇÃO B — Intermediária: Usuário copia o token manualmente do browser
    O portal explica passo a passo como o usuário pode abrir o JD Warranty,
    fazer login, abrir o DevTools (F12) e copiar o token das requisições.

  OPÇÃO C — Avançada: Browser remoto com noVNC no servidor
    O servidor roda o Chrome + Selenium num container Docker com VNC, e o
    usuário vê e controla o browser diretamente pelo portal via noVNC.
    (Mais complexo, mas 100% self-contained no servidor)

RECOMENDAÇÃO PARA A MAQNELSON: usar a OPÇÃO A no início (mais rápida de
implementar e já funciona com o que vocês têm), evoluindo para OPÇÃO C
futuramente se quiserem eliminar qualquer script local.

PARTE 6 — ENDPOINTS DA API BACKEND (FastAPI)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  POST   /api/validate-token
    → Recebe o Bearer Token, faz uma requisição de teste na API JD
    → Retorna: { "valid": true/false, "message": "..." }

  POST   /api/upload
    → Recebe o arquivo .xlsx (multipart/form-data)
    → Valida se existe coluna "chassi"
    → Retorna: { "job_id": "uuid-aqui", "total_chassis": 25 }

  POST   /api/iniciar/{job_id}
    → Dispara a tarefa Celery em background
    → Retorna: { "status": "queued" }

  GET    /api/progresso/{job_id}
    → Server-Sent Events (SSE) — stream de progresso em tempo real
    → Envia eventos: { "chassi": "...", "linhas": 47, "atual": 18, "total": 25 }

  GET    /api/resultado/{job_id}
    → Retorna o arquivo Excel para download
    → Content-Type: application/vnd.openxmlformats...

  GET    /api/status/{job_id}
    → Retorna o estado atual da tarefa: queued / running / done / error

PARTE 7 — SOLUÇÃO DETALHADA PARA O LOGIN OKTA (O PONTO CRÍTICO)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  OPÇÃO A — Token Helper Local (RECOMENDADA para início)
  ───────────────────────────────────────────────────────

  O usuário roda uma vez na própria máquina um script mínimo:

    python token_helper.py

  O script:
    1. Abre o Chrome na máquina do usuário
    2. O usuário faz login no JD Warranty System normalmente (com Okta)
    3. O script intercepta o Bearer Token (já existe em scraper.py!)
    4. Exibe o token no terminal em uma caixa clara:

       ┌─────────────────────────────────────────────────────────────┐
       │  TOKEN CAPTURADO — Copie e cole no portal:                  │
       │                                                             │
       │  Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiO... │
       └─────────────────────────────────────────────────────────────┘

    5. O usuário copia o token e cola na Tela 1 do portal

  Vantagens:
    + Reusa 100% o scraper.py já existente (quase sem código novo)
    + O token dura várias horas — o usuário faz isso 1x por sessão
    + Sem complexidade de VNC ou browser remoto

  Desvantagens:
    - Requer que o Python esteja instalado na máquina do usuário
    - Pode-se distribuir como um .exe (já sabemos fazer com PyInstaller!)


  OPÇÃO B — Cópia manual pelo DevTools (sem script)
  ──────────────────────────────────────────────────

  O portal exibe um guia em vídeo/GIF ou imagens mostrando:
    1. Abra jdwarrantysystem.deere.com no Chrome
    2. Faça login normalmente
    3. Pressione F12 → aba "Network"
    4. Clique em qualquer requisição para "api/products"
    5. Em "Headers", copie o valor de "Authorization"
    6. Cole no campo do portal

  Vantagens:
    + Zero instalação extra
    + Funciona em qualquer máquina
  Desvantagens:
    - Requer mais instrução ao usuário


  OPÇÃO C — Browser remoto com noVNC (AVANÇADA)
  ──────────────────────────────────────────────

  O servidor Docker tem:
    - Selenium + Chrome em container com Xvfb (tela virtual)
    - noVNC (converte VNC para WebSocket — acessível pelo browser)

  Fluxo no portal:
    1. Usuário clica "Fazer Login"
    2. Abre um iframe/popup mostrando o browser remoto em tempo real
    3. Usuário vê o Chrome rodando no servidor e faz o login normalmente
    4. O token é capturado automaticamente no servidor
    5. Iframe fecha, token fica salvo na sessão do portal

  Vantagens:
    + 100% web — nenhum script local
    + Experiência idêntica ao desktop atual
  Desvantagens:
    - Maior complexidade de setup (Docker + VNC + noVNC)
    - Consome mais recursos do servidor
    - Pode ter latência de vídeo dependendo da conexão

  ─────────────────────────────────────────────────────────────────────────────
  ETAPA 1 — Preparar o backend FastAPI (2-3 dias de desenvolvimento)
  ─────────────────────────────────────────────────────────────────────────────

  1.1 — Criar o projeto e instalar dependências:

    pip install fastapi uvicorn celery redis python-multipart openpyxl
    pip install pandas requests mysql-connector-python python-dotenv

  1.2 — Criar backend/main.py com os endpoints listados na Parte 6.

  1.3 — Adaptar processor.py:
    - Receber token como parâmetro (não mais do scraper)
    - Adicionar callback de progresso que publica no Redis
    - Retornar bytes do Excel em vez de salvar em caminho fixo

PARTE 10 — OPÇÕES DE HOSPEDAGEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  OPÇÃO 1 — Servidor interno da Maqnelson (RECOMENDADA)
    ✔ Já tem acesso à VPN e ao banco MySQL interno
    ✔ Sem custo extra de cloud
    ✔ Mais simples para segurança (não expõe dados para fora)
    → Precisa de um servidor Windows ou Linux com Docker instalado
    → Acessível pela rede interna (ou via VPN para home office)

  OPÇÃO 2 — VPS Cloud (AWS, Azure, Google Cloud, DigitalOcean)
    ✔ Alta disponibilidade
    ✔ Acesso de qualquer lugar sem VPN
    ⚠ O banco MySQL precisa ser acessível da cloud (túnel, whitelist de IP, ou
      migrar o banco para cloud também)
    ⚠ Custo mensal (~R$50-200/mês dependendo do provedor)

  OPÇÃO 3 — Máquina de um funcionário como servidor temporário
    ✔ Zero custo
    ✔ Funciona para testes e uso interno
    ⚠ Fica offline quando o computador desliga
    → Útil apenas para POC (prova de conceito)

  OPÇÃO 4 — Docker Desktop local (para desenvolvimento/testes)
    → Instalar Docker Desktop no Windows
    → Rodar docker-compose up
    → Acessar localhost:8000

PARTE 11 — SEGURANÇA E BOAS PRÁTICAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ✔ O token Bearer da JD NUNCA é armazenado no banco — fica apenas na sessão
    do usuário (memória Redis com TTL curto, ex: 4 horas)

  ✔ O arquivo .env com credenciais do banco NUNCA vai para o Git
    → Adicionar .env no .gitignore

  ✔ Uploads de arquivo devem validar:
    → Extensão (somente .xlsx)
    → Tamanho máximo (ex: 5MB)
    → Leitura com engine="openpyxl" (não executa macros)

  ✔ Os arquivos temporários (uploads + resultados) devem ter limpeza automática
    → Deletar após X horas ou após download confirmado

  ✔ Se exposto na internet: adicionar autenticação básica no portal
    → HTTP Basic Auth, ou login simples com usuário/senha fixos no .env

  ✔ HTTPS obrigatório se exposto fora da rede interna
    → Usar Certbot (Let's Encrypt) com NGINX gratuitamente

  ✔ O portal não deve logar o token completo nos arquivos de log do servidor

================================================================================
   CONCLUSÃO
================================================================================

O JD Extractor é um RPA bem estruturado. A migração para portal web é
totalmente viável — grande parte do código Python existente (processor.py,
db_inserter.py) é reaproveitada sem alterações significativas.

O único ponto de atenção é o login Okta, que exige interação humana real.
A solução mais pragmática é o "token_helper.exe" que o usuário roda 1 vez
por sessão na própria máquina, copia o token e cola no portal.

Com 6-8 dias de desenvolvimento, é possível ter um portal web funcional,
hospedado internamente na Maqnelson, acessível pelo browser de qualquer
computador da rede, com progresso em tempo real e download do Excel.
